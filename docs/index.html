PAGE 03Workloads & Deployment Strategies

Choosing the right controller, and rolling out changes safely.

StatefulSet vs Deploymentidentity matters
StatefulSet ↓ mysql-0 mysql-1 mysql-2 ← each gets: stable name · stable DNS · stable storage
MEMDeployment = replaceable Pods (stateless)  ·  StatefulSet = identity matters (databases)
💡
Why: a MySQL cluster where mysql-0 is the primary and mysql-1/2 are replicas — each Pod must keep the same name, network identity, and disk across restarts, or replication breaks. A Deployment would recreate Pods with random names and no guarantee of the same storage.
✎Your notes: 25th-July full-stack project — nginx + Node.js frontend/backend Deployments in front of a MySQL StatefulSet, exactly this split.
DaemonSetone per node
Node 1 → Monitoring Pod Node 2 → Monitoring Pod Node 3 → Monitoring Pod
kubectl get daemonsets

List DaemonSets.

MEMDaemonSet = every node needs one — log collectors, monitoring agents, security agents
💡
Why: you want a Fluentd or node-exporter Pod on every node automatically, including new nodes the Cluster Autoscaler adds later — a Deployment with a fixed replica count can't guarantee "exactly one per node."
Job & CronJobrun-to-completion
kubectl get jobs

Run a task until completion.

kubectl get cronjobs

Run a task on a schedule.

MEMDeployment=keep running  Job=run once  CronJob=run repeatedly on schedule
💡
Why: a one-off database migration script → Job (runs to completion, then stops). A nightly backup of that same database → CronJob (same idea, on a schedule). Neither should be a Deployment — you don't want it restarting forever.
Probeshealth checks
Container starts ↓ Startup Probe → has the app started? ↓ Readiness Probe → can it receive traffic? ↓ Receive Traffic ↓ Liveness Probe → continuously: is it still alive?
MEMSTARTUP=started?  READINESS=traffic?  LIVENESS=alive?
✎Your notes: 20th-July session paired Headless Services with Probes — readiness gates matter most for StatefulSet Pods behind a headless Service.

Servicesstable endpoint
Users ↓ Service ← stable network endpoint for dynamic Pods ↓ Pods
ClusterIP

Internal-only communication (default).

NodePort

Reachable at NodeIP:Port.

Provisions an external cloud load balancer.

ExternalName

DNS alias to an outside service.

Headless (clusterIP: None)

Direct Pod DNS — used for StatefulSet discovery.

kubectl expose deployment nginx --port=80 --type=ClusterIP

Create a Service from an existing Deployment.

💡
ClusterIP: your backend API only needs to be reachable by the frontend Pods inside the cluster — no outside access at all.
NodePort: quick manual test on a dev cluster, hitting <NodeIP>:30080 before you've set up a load balancer.
LoadBalancer: a production app on EKS that the public internet needs to reach — provisions an actual AWS ELB.
Headless: your MySQL StatefulSet Pods need individually addressable DNS names (mysql-0.mysql) for replication, not one shared IP.

IngressHTTP/HTTPS routing
Internet → DNS → Cloud Load Balancer ↓ Ingress Controller (NGINX · HAProxy · AWS LB Controller) ↓ Ingress Rules → Service → Pods AWS path: ALB + ACM (TLS cert) → AWS Load Balancer Controller → Ingress
MEMService = expose the application  ·  Ingress = HTTP/HTTPS routing on top of it
💡
Why: you have api.example.com and app.example.com both needing TLS, but you don't want a separate cloud load balancer (and its cost) per app. One Ingress + one ALB routes by hostname/path to the right Service, and ACM handles the certificate centrally.

PAGE 05Storage & Stateful Workloads

From a raw disk to a mounted volume inside a Pod.

PV / PVC chainstorage binding
Physical / Cloud Storage ↓ PersistentVolume (PV) ← storage resource ↓ PersistentVolumeClaim (PVC) ← storage request ↓ Pod Dynamic provisioning: StorageClass → Dynamic Provisioning → PV → PVC
kubectl get pv

List PersistentVolumes.

kubectl get pvc

List PersistentVolumeClaims.

kubectl get storageclass

List StorageClasses.

kubectl describe pvc <name>

Why is a PVC stuck Pending?

MEMPV=storage resource  PVC=storage request  StorageClass=how storage gets created
💡
Why: your MySQL StatefulSet Pod gets rescheduled to a different node after a crash — without a PVC bound to a PV, its data disk would be gone. The PVC claims storage on the Pod's behalf; a StorageClass means you never had to hand-create the PV — EBS just provisions it on demand when the claim is made.
